## Executive Finding

The number `31` is a prerelease sequence, not a count of independent code defects. Phase 1 had already published through beta.20. Phase 2 selected beta.21 through beta.31: ten candidates were invalidated and beta.31 succeeded. The high visible count came from a strict rule that permanently consumed an immutable beta identity after any failed gate, source/test correction, environment mistake, transient process failure, or first anonymous availability race.

The root cause is a combination of:

1. **Under-designed end-to-end release boundaries:** Plan 02-41 declared the toolchain source-complete before candidate selection, but real assembly, GitHub publication, fresh-receipt and CDN behavior exposed several untested semantics afterward.
2. **Over-rigid prerelease identity policy:** Plan 02-38 selected `beta.N` before running the complete quality suite and required a new version after every failure, including test-fixture, host-runtime and transient OS failures.
3. **Insufficient realistic rehearsal:** Unit/contract fixtures did not initially cover the real dependency closure, GitHub's absent-tag 422 response, public-versus-consumed version sets, volatile receipt timestamps, or CDN eventual consistency.

Product scope did not materially drift: the work remained in local installation, signed beta publication, update verification and hard human gates. Execution scope did drift inside the release subsystem: plans that declared receipt-only outputs repeatedly had to edit release tooling, test harnesses and supporting runtime code. The result was release-process churn rather than expansion into unrelated product capabilities.

## Was This Over-Design or Under-Design?

**Both, in different layers.**

- **Over-designed constraints:** immutable selection before QA, permanent consumption after any failure, full-chain rerun for test-only/environment failures, and a one-shot full availability verifier. These guarantees are stronger than needed for an internal prerelease candidate.
- **Under-designed lifecycle:** the design did not sufficiently model self-referential archive metadata, real dependency names, GitHub 422 semantics, public-versus-consumed state, volatile timestamps and CDN propagation before declaring the release source frozen.
- **Scope control:** product scope remained bounded. The divergence was within the release/verification subsystem: it became much larger and more central than the original user-visible goal warranted.

A concise diagnosis is: **the project over-designed release guarantees while under-designing the release rehearsal that should validate those guarantees before version lock.**

## Root Cause

The immediate root cause was premature immutable candidate selection on a release pipeline that had not yet passed a realistic end-to-end rehearsal. The structural root cause was coupling version identity, repository commit, all tests, signed archives, prompt, publication and anonymous availability so tightly that every correction— including fixture and environment corrections—forced a new beta and a complete downstream rebuild. Strict fail-closed rules made failures visible and prevented unsafe claims, but also amplified modest defects into long release loops.

## Recommended Actions

1. **Introduce a pre-candidate rehearsal stage.** Run full managed-runtime suites, real dual-target assembly, signed-manifest/preflight checks and a simulated/recorded GitHub lifecycle before assigning `beta.N`.
2. **Assign immutable beta versions only after local quality and assembly pass.** Use an internal build/RC identifier for earlier attempts; consume public `beta.N` only once the source and artifacts are frozen.
3. **Separate failure classes.** Product/source failure, test-fixture failure, runner/environment failure, transient external failure and public-release failure should not all have the same version-consumption consequence.
4. **Keep public immutability strict.** Once a tag/release exists, never overwrite it. The recommendation is to relax pre-publication identity consumption, not public artifact integrity.
5. **Add a release-boundary rehearsal suite.** It must cover actual package closure names, GitHub 404/422 behavior, public-versus-consumed histories, volatile receipt fields, redirect/CDN readiness and one-shot verifier invocation.
6. **Enforce the managed runtime centrally.** Release gates should make raw host `npm` invocation impossible rather than relying on executor discipline.
7. **Quarantine or preflight flaky OS tests before candidate lock.** Run the process-observation and fixed-port lifecycle groups before selecting an immutable candidate; retain fail-closed behavior for the final run.
8. **Require an explicit release architecture freeze review.** Before a future Plan 02-38 equivalent, verify that later plans truly make outputs only. If a downstream plan needs source edits, return to design/rehearsal before selecting a version.
9. **Use stage-specific safe failure codes.** Replace generic `PHASE2_AVAILABILITY_FAILED` diagnostics with redacted stage codes for metadata, readiness, redirect, bytes, signature and closure, so external races are diagnosed before consuming additional public versions.
